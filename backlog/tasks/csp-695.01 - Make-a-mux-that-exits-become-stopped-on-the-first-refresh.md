## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
After detaching from or killing a mux, the row does not become a stopped mux until the operator refreshes by hand. The earlier fix cleared the tmux listing cache and re-probed after attach, but the symptom remains, so the cause is elsewhere or the fix is not on the path the operator uses. It needs a reproduction against a real terminal session, not only unit tests.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Root cause: inside tmux, attach is switch-client, which returns at once. The one post-attach refresh ran while the mux was still alive, and nothing refreshed when the operator switched the client back, so an exited mux stayed on screen as running until the timer (default 30s) or a manual refresh. The earlier cache fix was right but did not cover this flow; the outside-tmux flow (attach-session blocks) already converged. Also, requested refreshes were only started from key-press dispatch, so a request raised without a key press would have waited for the next key. Fix: a watcher thread polls tmux for the TUI pane's visibility (session attached, window and pane active) and raises ViewRegained when it comes back; requested refreshes now start from the loop's drain as well as from dispatch. Verified by 11 end-to-end tests that drive the real TUI in a private tmux server (tests/tui_tmux_e2e.rs; four inside-tmux cases fail without the watcher) and the scratch check tui_mux_exit_roundtrip.
<!-- SECTION:NOTES:END -->

## Final Summary

<!-- SECTION:FINAL_SUMMARY:BEGIN -->
Root cause: inside tmux, attach is switch-client and returns immediately, so nothing refreshed after the operator switched back. A pane visibility watcher now forces a mux re-probe on return; verified by a real-tmux end-to-end suite.
