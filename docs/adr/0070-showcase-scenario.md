# ADR 0070: Showcase Scenario For Comprehensive Functionality Exercise

## Status

Accepted

## Context

`src/dev_scenarios.rs` ships nine curated worlds (empty,
orphan-session, exact-match, ambiguous-mux, hook-supersession,
codex-fd-current, process-cardinality, workspace-pr,
fork-lineage). Each is intentionally narrow — built to exercise
one resolver edge case in isolation, useful for regression-test
support and visual inspection of that one behavior.

What's missing is a *comprehensive* world: one curated scenario
that lights up most of conspectus's surfaces at once
(workspaces, all three+ agent harnesses, forks, PRs, mux
ambiguity, hook supersession, parent-session chains, bare repos
with linked worktrees). Such a world serves two purposes:

1. **Onboarding surface.** A new contributor running
   `conspectus dev-scenario tui --name showcase` sees most of
   what conspectus does in one screenful, with no live state
   needed.
2. **Demo / iteration baseline.** A stable, machine-independent
   world to point the snapshot/fixture tools at when
   demonstrating a feature or iterating on the renderer.

## Decision

Add a `"showcase"` scenario to `dev_scenarios::SCENARIOS`. It is
built from modular sub-functions so adding a new edge case later
is a single call rather than a wholesale rewrite. The scenario
covers:

- **Workspaces**: an atelier workspace with member repos and a
  fork lineage; an agent-deck workspace with symlinked checkouts
  and a profile `state.db` that names the workspace per ADR
  0066; a generic loose workspace discovered from a scan-root
  with sibling repos.
- **Repos and checkouts**: a normal repo with main + feature
  branches; a bare repo with a linked worktree on disk; a repo
  with a remote so the branch-to-PR resolution path runs.
- **Agent sessions**: codex JSONL with a parent → child fork
  lineage chain (ADR 0018); claude-code JSONL attached to a mux;
  opencode `info.json` under a member repo; aider per-cwd state;
  an orphan session whose cwd resolves to no checkout.
- **Mux**: an attached pane with one agent; an unmuxed agent
  session; an ambiguous mux with two harness candidates;
  agent-deck workspace launch composite-dir cwd.
- **Forks**: an atelier fork recorded in
  `.atelier/forks/index.toml` with a `parent_session` link to a
  codex session.
- **Forge**: an open PR on one repo; a draft PR on another.
- **Hook supersession**: a hook record demonstrating the
  freshest session winning over a stale `--resume` argv.

The scenario is reachable through two surfaces:

1. `conspectus dev-scenario tui --name showcase` — interactive,
   debug-only.
2. **A checked-in fixture at `tests/fixtures/showcase.json`** —
   the same world serialized after `resolve_snapshot`, suitable
   for `conspectus tui --fixture tests/fixtures/showcase.json`
   without needing a debug build. The JSON is regenerated by a
   `just regen-showcase-fixture` recipe that runs
   `dev-scenario graph --name showcase --format json` and pipes
   it to the file.

### Evolution rule

When a new edge case is discovered in conspectus that the
showcase doesn't exercise, the expectation is:

1. Add a sub-function (`add_X_to_showcase(world)`) that injects
   the case into the existing world.
2. Call it from `build_showcase`.
3. Re-run `just regen-showcase-fixture` so the checked-in
   fixture matches.

This is the maintenance contract; the showcase is intended to
grow over time.

### Why not split into multiple scenarios

Splitting "showcase-workspaces", "showcase-sessions", etc.
keeps each piece smaller but defeats the onboarding purpose —
the value of one screenful that shows "look, this is what
conspectus does" is what makes the showcase useful. Smaller
focused scenarios already exist (and will continue to be
added); the showcase is the umbrella that exercises them
together.

## Consequences

- **Onboarding shortcut.** New contributors and operators get a
  fast visual tour of conspectus by running one command.
- **Stable demo state.** Documentation, screencasts, and bug
  reports can reference a known fixture instead of
  hand-screenshotting a temporary live state.
- **Wider regression surface.** A nextest pins the showcase's
  build path; if a future model or resolver change breaks any
  layer in the showcase, the test surfaces it.
- **`ScenarioWorld` gains primitives.** Two new helpers — bare
  repo with linked worktree, agent-deck workspace — land
  alongside the showcase so future scenarios can reuse them.
- **Checked-in JSON drifts.** The fixture is regenerated by a
  `just` recipe; the test suite does not auto-regenerate. If a
  developer's change to the showcase forgets to re-run the
  recipe, `git diff` flags the mismatch.

## Alternatives Considered

### A. Hand-craft `tests/fixtures/showcase.json` directly

Skip the programmatic builder, write the JSON by hand. Rejected
because every new edge case becomes a JSON merge instead of a
Rust function, and provider schemas evolve (the fixture would
drift from real shapes).

### B. Build the showcase from `tests/fixtures/` corpus files

Use the captured-fixture corpus already in `tests/fixtures/` as
inputs. Rejected — the corpus is real-data sanitized for
schema-drift detection, not curated to exercise specific
resolver branches. Mixing the two purposes makes both worse.

### C. Make the showcase auto-regenerate at test time

A pre-build script that always regenerates the fixture before
tests run. Rejected — generated state in the repo invites merge
conflicts, and the regen is fast enough to be a manual `just`
step.

## Open Questions

- Should the showcase eventually inject session pins (ADR 0057)
  and session continuity sidecars (ADR 0058)? Yes when the
  showcase's scope of "everything conspectus does" warrants it;
  out of scope for V1 because pins write to user config and
  injecting them cleanly into a temp world needs additional
  scaffolding.
- Should the showcase fixture be parameterized (per-OS path
  normalization, optional layers)? Defer until a real demand
  surfaces. Today it's one fixture, one world, deterministic
  paths under `/fixture`.
