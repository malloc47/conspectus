# ADR 0018: Intra-Harness Session Lineage

## Status

Accepted. Extends ADR 0005.

## Context

ADR 0005 represents session lineage as `parent_session` / `child_session`
relation candidates whose source is a `Fork` node. That shape fits Atelier:
Atelier records a `ForkEntry` whose harness entries carry source and fork
session ids, and one fork can affect several harnesses, repos, and checkouts,
so a polymorphic `Fork` node is a natural anchor.

Harnesses themselves also produce session lineage that is *not* fork-shaped:

- `claude-code` writes a `parentUuid` on the first message of each JSONL
  transcript when the session was compacted from, or resumed out of, an
  earlier transcript in the same project.
- `opencode` records `session.parent_id` in its SQLite store when a session
  was spawned from another.
- `codex` may record a resume pointer (TBD per `CSP-120`).

These events have no provider-recorded fork metadata, no context effect, and
no operation that the user would call "a fork." They are intra-harness
continuations. ADR 0005 leaves it ambiguous whether such links should be
anchored at a synthetic `Fork` node (to keep lineage uniform with the
fork-anchored shape) or attach directly between two `AgentSession` endpoints
(simpler queries, no synthetic provenance node).

A synthetic `Fork` per compaction or resume would also create one fork node
per intra-harness continuation event for every supported harness, which can
easily exceed the number of fork nodes generated by Atelier itself. The
design.md "Fork effect matrix" lists "no context, no session, metadata only"
as a noop — synthetic forks with neither provider-side fork metadata nor
context effects sit close to that row and would dilute the meaning of
`Fork`.

Separately, Atelier today writes `lineage_kind` to source metadata with the
values `native`, `approximate`, `unsupported`, `fresh`. Those describe the
*fidelity* of the lineage attribution, not the operation type. Introducing
operation-type vocabulary (compaction, resume, fork) under the same field
name would silently overlap with the existing usage.

## Decision

Allow `parent_session` and `child_session` relation candidates to attach
directly between two `AgentSession` endpoints, without a `Fork` node in
between, when the lineage was produced by an intra-harness mechanism such as
compaction or resume. Fork-anchored lineage from Atelier and any future
fork-shaped provider continues to work exactly as ADR 0005 specifies.

Emission direction:

- The discovered side emits one outgoing `parent_session` candidate from the
  child session to the parent. The inverse `child_session` link is not
  emitted from intra-harness sources; consumers traverse `parent_session`
  edges in either direction.
- Atelier and other fork-anchored providers continue to emit both
  `parent_session` and `child_session` candidates from a single `Fork` when
  the fork record carries both endpoints.

Endpoint resolution follows ADR 0005:

- When the parent `AgentSession` node is present in the same snapshot, the
  target is `LinkEndpoint::Node`.
- When the parent is missing (pruned transcript, dropped SQLite row, parent
  outside the scan), the target is `LinkEndpoint::Unresolved` carrying
  `harness_key`, the provider-native parent id, and any path / state-scope
  hints the adapter can supply.
- The resolver emits a `Diagnostic::UnresolvedEndpoint` for unresolved
  candidates and a concrete `ResolvedRelationship` when both endpoints are
  real `AgentSession` nodes. No placeholder `AgentSession` nodes are
  invented.

Vocabulary for the `lineage_kind` field on `GraphLink::source_metadata`
fields (and the mirrored field on `UnresolvedEndpoint::metadata`):

- `fork`: the parent was explicitly forked into the child (Atelier-style;
  the provider names the operation a fork).
- `compaction`: the child is the post-compaction successor of the parent;
  the parent's context was summarized into the child's prelude.
- `resume`: the child was started by an explicit resume operation against
  the parent.
- `fresh`: the provider records that the session was started without a
  parent. Already used by Atelier (ADR 0005). No `parent_session` candidate
  is emitted in this case.
- `unknown`: the provider records a parent pointer but the adapter cannot
  classify the operation.

These values are operation types. Adapters that also need to record how
trustworthy the lineage attribution is must use a separate `lineage_fidelity`
field with vocabulary `native`, `approximate`, `unsupported`. Atelier's
existing `lineage_kind` field currently carries those fidelity values; the
CSP-118 implementation phase will rename Atelier's emission to
`lineage_fidelity` and set `lineage_kind = "fork"` (or `"fresh"`) so the two
namespaces no longer collide. Snapshot fixtures will be regenerated as part
of that change.

`source_metadata.fields.harness_key` continues to identify the emitting
harness on every intra-harness lineage candidate, matching the convention
the harness adapters already follow.

## Consequences

- `parent_session` and `child_session` relation candidates may now have an
  `AgentSession` source as well as a `Fork` source. The resolver, projection
  layer, and any tooling that walks lineage edges must accept either shape.
- Intra-harness compaction and resume produce no `Fork` nodes, keeping the
  fork node population proportional to provider-recorded fork operations.
- Atelier's existing fork-anchored lineage is unchanged at the data-model
  level. The `lineage_kind` rename is a source-metadata field change with
  snapshot churn but no relation-kind change.
- Snapshot fixtures and any code reading `source_metadata.fields.lineage_kind`
  to discriminate Atelier capability tiers must be updated when the rename
  lands.
- Resolver behavior and the `UnresolvedEndpoint` shape do not change. The
  existing `unresolved_lineage_links_are_preserved` and
  `unresolved_endpoint_becomes_diagnostic_not_relationship` tests continue
  to apply.
- `docs/design.md` should reflect that session lineage edges may be either
  fork-anchored or directly between two `AgentSession` nodes.

## Alternatives Considered

- **Synthesize a `Fork` node for each intra-harness lineage event.** Keeps
  lineage uniform with the fork-anchored shape but inflates the fork node
  population, conflicts with the `Fork` semantics in ADR 0003 / design.md
  (which describes Fork as a provenance concept anchored on a
  provider-recorded operation), and forces consumers to walk two edges to
  follow a simple compaction chain.
- **Treat compaction/resume as a separate relation kind such as
  `succeeded_by`.** Rejected because the relationship is the same one ADR
  0005 already models — one agent session is the continuation of another —
  and adding a parallel relation kind would split lineage queries across
  two enums without semantic benefit.
- **Emit both `parent_session` and `child_session` from intra-harness
  sources.** Rejected as redundant: every adapter that knows a parent can
  walk from the child node; emitting both doubles candidate counts and
  invites resolver duplication. Fork-anchored providers keep emitting both
  because the fork is a third node that knows both endpoints; intra-harness
  links have no such third node.
- **Reuse Atelier's `lineage_kind` values for the operation type.** Rejected
  because `native` / `approximate` / `unsupported` describe attribution
  fidelity, not the operation. Conflating them would make compaction and
  resume indistinguishable from Atelier's existing capability tiers.

## Open Questions Answered

- Intra-harness `parent_session` / `child_session` links attach directly
  between two `AgentSession` nodes; no synthetic `Fork` is introduced.
- The discovered side emits one `parent_session` candidate from the child.
- `lineage_kind` vocabulary is `compaction`, `resume`, `fork`, `fresh`,
  `unknown`. Fidelity moves to `lineage_fidelity`.
- Unresolved parent evidence preserves `harness_key` and the provider-native
  parent id, matching ADR 0005's `UnresolvedEndpoint` shape.
- Atelier lineage emission is unchanged at the relation level; only the
  source-metadata field name moves.
