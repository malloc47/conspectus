# Live state research 04: Pi

Research notes for the live-state feature, harness `pi` (ADR 0121).
Scope: per-harness signal extraction only. The graph representation and
TUI surfacing are later steps. Nothing here is a decision; each
recommendation needs an ADR before it lands.

  **1.5.2 (2026-11-10)**, repository `github.com/earendil-works/pi`

## TL;DR

1. **Pi already computes the state we want.** The interactive TUI's
   `ProgramStatusReporter` derives `working`, `blocked` (kinds
   `permission`, `question`, `auth`), `done`, `error`, and `idle` from
   its own session events, and reports them as OSC 7501 [S3][S4].
   tmux does not forward OSC 7501 [S4], so Conspectus can't see those
   reports. A Conspectus extension can rebuild the same state from
   extension events, which carry the same information.
2. **"Waiting" in Pi means an extension dialog is open.** Pi has no
   built-in tool-approval prompt [S5]. Waiting on the operator happens
   only when an extension calls `ctx.ui.select/confirm/input/editor/custom`
   (permission gates, question tools, plan-mode approval). Each such call
   fires `ui_prompt_start` / `ui_prompt_end` (since 0.84.4) [S2][S6][S7].
   A model that ends its turn with a question in plain text is READY;
   Pi reports that as `done`.
3. **Subagents are not built in** [S8]. The reference `subagent`
   example extension runs child `pi --mode json -p --no-session`
   processes behind one long `subagent` tool call [S9]. To an observer
   that is a tool execution named `subagent`, plus child `pi` processes
   under the parent.
4. **The session file tail is a fair fallback.** Pi appends each entry
   synchronously at `message_end`, with no buffering [S10][S11]. The last
   record tells "model generating" from "tools running" from "turn
   finished". It cannot show WAITING or COMPACTING, and the default idle
   cache warming writes `usage` entries for up to 30 minutes after a run
   [S12][S13], so mtime is not activity.
5. **Two problems in the existing hook path need fixing first.** The
   spool keys records per tmux *session*, not per pane, so two Pi panes in
   one tmux session overwrite each other. And handlers that spawn on
   every event would sit in Pi's awaited handler chain [S6]. Recommended
   design: the extension keeps a small state machine and sends a
   self-contained state snapshot to `conspectus hook write pi`, only on
   transitions plus a heartbeat. Each snapshot carries `pid`, `seq`, and
   millisecond time, and the spool keys records per pane.

## 2. Pi's own state model (the reference)

`packages/coding-agent/src/modes/interactive/program-status-reporter.ts`
[S3] is fed every `AgentSessionEvent` by `interactive-mode.ts`
(`this.programStatus.handleEvent(event)`, unfiltered) [S14]. It computes,
in priority order:

1. **blocked**, when any blocked source is registered. The most recent
   one wins and supplies `kind` and `message`.
2. **working** with message "Compacting context", while
   `compaction_start` has not been followed by `compaction_end`.
3. **working**, while `runActive`. `agent_start` sets it and
   `agent_settled` clears it.
4. Otherwise the resting status:
   - **done** when the last assistant `message_end` had a stop reason
     other than `error`.
   - **error** when it was `stopReason === "error"`. The message is the
     first line of `errorMessage`.
   - **idle** when `agent_settled.aborted` is set, at startup, and after
     a cancelled compaction.

Retries: an errored response sets the pending outcome to error, and a
later success overwrites it. Because `runActive` stays true, the terminal
shows working for the whole retry span. The error shows only if it is
still the outcome at `agent_settled` [S3].

Blocked sources and their kinds, from `interactive-mode.ts` [S14]:

| Source | Kind | Visible to an extension? |
|---|---|---|
| `ctx.ui.confirm` | `permission` | Yes: `ui_prompt_start{kind:"confirm"}` |
| `ctx.ui.select`, `input`, `editor` | `question` | Yes: `ui_prompt_start{kind}` |
| `ctx.ui.custom` inline, with `options.blocked` | the caller's kind | Partly. `ui_prompt_start{kind:"custom"}` fires for **every** `custom()` call, blocking or not, and does not carry `blocked` [S6]. |
| `ctx.ui.custom` overlay, with `options.blocked` | the caller's kind | Same as above |
| Provider login (OAuth / API key) | `auth` | **No.** It's internal (`setBlocked("login", …)`) and doesn't go through the extension UI context [S14]. |
| Built-in selectors (`/model`, `/tree`, `/resume`, settings, `/trust`) | none (not blocked) | No [S14] |
| Project-trust prompt at startup | `question`, through the extension UI functions | Fires before `session_start` [S2], so the session isn't known yet. |

The OSC 7501 wire format, for reference:
`ESC ] 7501 ; state=<s>:kind=<k>:app=<a>:msg=<base64> ST`. States are
`idle`, `working`, `done`, `blocked`, and `error`, plus `clear`. Blocked
kinds are `permission`, `question`, and `auth` [S15]. Pi sends it only
after the terminal answers a support query, or always with
`PI_PROGRAM_STATUS=1`; `PI_PROGRAM_STATUS=0` turns it off. Reports
"never contain prompts or model output". "tmux and screen do not forward
them" [S4]. The reporter was added in 1.1.0 (2026-10-07) [S13].

**Takeaway.** The protocol's vocabulary (`working`, `blocked(kind)`,
`done`, `error`, `idle`) is a ready-made, privacy-clean, cross-harness
vocabulary. The canonical Conspectus states could align with it. That's a
question for the graph step.

Context available to handlers [S2][S7]:

- `ctx.mode`: `tui`, `rpc`, `json`, or `print`.
- `ctx.hasUI`: true in TUI and RPC.
- `ctx.isIdle()`: false during a run, an automatic retry, an
  auto-compaction retry, or a queued continuation. Since 1.2.0 it's also
  false while a run starts [S2][S13].
- `ctx.hasPendingMessages()`.
- `ctx.getContextUsage()`.
- `ctx.sessionManager`: `getSessionId()`, `getSessionFile()`, `getCwd()`,
  `getSessionName()`.

`process.pid` is plain Node, available because extensions run in the Pi
process [S2]. Passing it in the payload removes the CSP-630 dependence on
`/proc/<pid>/comm` (INFERRED).

How Pi runs handlers, which constrains delivery [S6][S11]:

- Handlers run **sequentially and are awaited**: extensions in load
  order, each extension's handlers in registration order.
- For agent events, Pi awaits the extension handlers **before**
  subscribers and before persisting the entry. A slow handler delays the
  agent.
- Handler errors are caught and logged. `tool_call` is the exception.
- The UI prompt events are not awaited.
- A `ctx` captured earlier is "stale after replacement and will throw if
  used" [S2]. Timers must not call a captured `ctx` after
  `session_shutdown`.
- Timers and child processes must start in `session_start`, not in the
  factory, and be cleaned up in `session_shutdown` [S2].

### 3.2 What "waiting on the operator" means for Pi

- **No built-in permission prompts.** "Pi … does not ask for approval
  before every tool call" [S5]. So "waiting for permission" exists only
  when the operator installed a gate extension: the `permission-gate.ts`
  example blocks in `tool_call` on `ui.select` [S2]; a third-party gate
  might use `ui.confirm`.
- **Questions to the operator** come from tool extensions such as
  `question.ts` and `questionnaire.ts` (the latter uses `ui.custom`) [S2].
  They prompt *during* a tool execution, so WAITING must outrank WORKING.
- **Plan approval** in the `plan-mode` example runs
  `ctx.ui.select("Plan mode - what next?", …)` *inside its `agent_end`
  handler* [S18]. The run hasn't settled (`agent_settled` waits for that
  handler), so WAITING must also outrank "run active".
- **Ambiguous: `kind: "custom"`.** `ui_prompt_start` fires for every
  `ctx.ui.custom()` call, including non-blocking loaders. Pi's own
  reporter treats `custom` as blocked only when the caller passes
  `blocked`, and that flag is not in the event [S6][S19]. Report it as
  WAITING with low confidence (`kind=custom`), or as a separate
  "extension UI open" sub-state.
- **Undetectable:** provider login (`auth`), built-in selectors, and the
  startup trust prompt (§2).
- **Plain-text questions** at the end of a turn are READY. Telling them
  apart would mean reading message text (Tier 2), which is out of scope.

### 3.3 RPC and JSON mode events (not observable for pane sessions)

`--mode json` and `--mode rpc` print every `AgentSessionEvent` on stdout
[S20][S21]:

- `agent_start`, `agent_end{messages, willRetry}`, `agent_settled{aborted}`.
- `turn_*`, `message_*`, `tool_execution_*`.
- `queue_update{steering, followUp}`, `entry_appended{entry}`.
- `compaction_start{reason}`,
  `compaction_end{reason, result, aborted, willRetry, errorMessage?}`.
- `auto_retry_start{attempt, maxAttempts, delayMs, errorMessage}`,
  `auto_retry_end{success, attempt, finalError?}`.
- `summarization_retry_*`.
- RPC only: `extension_ui_request` / `extension_ui_response`,
  `extension_error`, `bash_execution_update`.

`get_state` returns `isStreaming`, `isCompacting`, `pendingMessageCount`,
`sessionFile`, `sessionId`, and more [S22].

Limits:

- These events stream only to the program that started Pi in that mode
  over stdio. There is no socket for attaching to an already running
  interactive Pi [S21].
- `auto_retry_*`, `compaction_*`, and `queue_update` go to subscribers
  only, **not to extensions** [S11].
- RPC Pi (`pi-rpc`) is a Background process that never claims a pane
  (ADR 0121).

So RPC/JSON is not a source for pane sessions. Two uses remain: these
names are the clearest vocabulary for fixtures, and an orchestrator that
drives Pi in RPC mode already has exact state (out of scope).

### 3.4 Session file tail records

Write timing, from `session-manager.ts` [S10] and `agent-session.ts`
[S11]:

- Nothing is written until the first `user` or `assistant` message. The
  header and all buffered entries are then written in one go (`openSync(…,
  "wx")`).
- After that, **each entry gets its own synchronous `appendFileSync`**,
  with no batching or debouncing.
- Messages (`user`, `assistant`, `toolResult`, `system`, custom) are
  appended on their `message_end`, after the extension handlers and
  subscribers have run.
- An errored assistant message is persisted **before** the retry
  decision. The failed attempt is then "durably omit[ted] from model
  projection" [S17]. That is probably a `context_edit` entry (INFERRED;
  the call site wasn't visible, so UNVERIFIED).
- Pi does not persist `pending` assistant messages [S16].

| Last meaningful entry (skip `custom`, `label`, `session_info`, `model_change`, `thinking_level_change`, `usage`) | Most likely state | Confidence |
|---|---|---|
| `message` role `user` | Model request in flight (WORKING, generating). Or Pi died before the reply. | Medium. Needs a live `pi` process. |
| `assistant`, `stopReason: toolUse`, some `toolCall` ids without a `toolResult` yet | Tools running (WORKING, tools). Or a gate extension is waiting in `tool_call` (WAITING). Indistinguishable. | Medium |
| `toolResult`, every `toolCall` id of the preceding assistant answered | Next model request in flight (WORKING) | Medium |
| `assistant`, `stopReason: stop` | Turn finished → READY. Could also be: queued follow-up about to start, plan-mode prompt in `agent_end` (WAITING), threshold auto-compaction running (COMPACTING). | Medium-high after a few seconds |
| `assistant`, `stopReason: length` | Overflow recovery compaction may run (COMPACTING), then a retry | Low |
| `assistant`, `stopReason: error` | Retry backoff (RETRYING) or settled ERROR. Retry defaults: `retry.maxRetries 3`, `baseDelayMs 2000`, `maxAgentDelayMs 60000` [S12]. Error older than about 60 s + margin, with no later entry → ERROR. | Medium |
| `assistant` error, then a `context_edit` targeting it | Retry in progress (INFERRED, UNVERIFIED) | Low until checked against a live Pi |
| `assistant`, `stopReason: aborted` | Operator pressed Esc → READY (interrupted) | High |
| `assistant`, `stopReason: deferred` | Provider will finish later (a deferred response with `pollAfterMs`) [S16]. Treat as WORKING (provider-pending). | Low (rare) |
| `compaction` | Compaction just finished. READY after manual or threshold compaction. WORKING if an overflow retry follows. | Low-medium |
| no file | Fresh session before the first exchange, or `--no-session` | n/a |

Tier 1 reading (ADR 0086): deserialize only `type`, `timestamp`,
`message.role`, `message.stopReason`, `message.toolCallId`, and the
`content[].type` / `content[].id` of tool calls. Never text, arguments,
or results. This is the same discipline the adapter's name scan follows.

## 4. Signal → canonical state mapping

Columns:

- **Hook**: the proposed extension.
- **Tail**: session file only.
- **Process/tmux**: no hook, no file.

Values: **C** certain, **A** ambiguous, **U** undetectable.

| Canonical state | Hook (proposed extension) | Tail | Process/tmux |
|---|---|---|---|
| WORKING: generating | **C**. `agent_start`, no tools in flight, no prompt. | A. Last entry `user` or fully answered `toolResult`. | A. `pi` alive. Can't tell from idle. |
| WORKING: tools | **C**. `tool_execution_start` without `parentToolCallId`, until the matching end. | A. `toolUse` with unanswered ids. Can't tell from a gate prompt. | A. Child processes, but MCP servers are false positives. |
| WAITING: permission / question | **C** for `confirm` / `select` / `input` / `editor` (`ui_prompt_start` until `ui_prompt_end`). **A** for `custom`. **U** for login. | **U** | **U** |
| WAITING: plan approval | **C** if the plan extension uses `ctx.ui` (the example does). Reported as WAITING/question, since the kind can't say "plan". | U | U |
| READY: turn finished | **C**. `agent_settled{aborted:false}` with last outcome not error, no prompt open. | A-high. `assistant stop`, then quiet. | U |
| READY: interrupted | **C**. `agent_settled{aborted:true}`. | C. `stopReason: aborted`. | U |
| READY: new / idle session | **C**. `session_start` with `ctx.isIdle()`. | U (no file before the first exchange) | A. `pi` in the pane. |
| SUBAGENTS ACTIVE | **A**. In-flight tool whose name is in a configured set (default `{"subagent"}`, the example's name [S9]). Pi has no subagent concept [S8]. A tool with nested `ctx.executeTool` calls (`parentToolCallId`, 0.99.0+) is "tool calling tools", not subagents. | A. A `subagent` toolCall pending. | A. Child `pi` processes under the Pi pid. |
| COMPACTING | **C**. `session_before_compact` until `session_compact` or `session_compact_failed`. | U while running. A after (`compaction` entry). | U |
| ERROR: run failed (settled) | **C**. `agent_settled` with the last assistant `stopReason: error`. Classify `errorMessage` locally. | A. `stopReason: error`, then quiet past the retry window. | U |
| ERROR: retrying | **C**. Assistant `error`, `agent_end`, run not settled, next `agent_start` pending. Attempt count not visible: `auto_retry_*` is subscriber-only [S11]. | A. `error` within the retry window, maybe a `context_edit`. | U |
| ERROR: rate limited | **C** when the provider returns HTTP 429 (`after_provider_response.status`). **A** from `errorMessage` classification. | A. Needs error text (Tier 2). Not recommended. | U |
| ERROR: compaction failed | **C**. `session_compact_failed{aborted:false, willRetry:false}`. | U | U |
| STARTING | **A**. Pi pid alive in the pane, no record from this pid yet. Trust prompt, resource loading, and package installs happen before `session_start`. | U | A. `pi` command, no record. |
| EXITED | **C** on a graceful exit: `session_shutdown{reason:"quit"}`, also sent on SIGTERM/SIGHUP through `shutdown({fromSignal:true})` [S14]. **U** from the hook on SIGKILL, crash, fatal runtime error (`process.exit(1)` without shutdown), and dead-terminal EIO (`process.exit(129)` that skips extension cleanup) [S14]. Backstop: pid liveness, which is **C**. | U | C. `pi` gone or the pid dead. |
| DETACHED (Pi-specific: `/new`, `/resume`, `/fork`, `/clone`, `/reload`) | **C**. `session_shutdown{reason≠quit}`, then `session_start`. | U | U |

## 5. Delivery, install, latency, reliability, versions

### 5.1 Where extensions load

Pi auto-discovers extensions [S2] from:

- `~/.pi/agent/extensions/*.ts|js`
- `…/extensions/*/index.ts|js`
- `…/*/package.json` with a `pi.extensions` field
- project `.pi/extensions/…`, loaded only after the project is trusted

The settings `extensions` (paths, `!pattern`, `+path`, `-path`) and
`packages` also load extensions [S12]. `PI_CODING_AGENT_DIR` moves the
agent dir (ADR 0121).

Extensions load in **every mode**. `ctx.mode` tells them apart [S2]. Pi
loads TypeScript through jiti with no build step [S2]. A changed
extension takes effect after a restart or `/reload` [S2], which fires
`session_shutdown{reload}` and then `session_start{reload}`.

### 5.2 Extending the existing plugin

Same file and same install path, so `hook init pi` / `hook status pi` /
`hook remove pi` stay as they are and bumping `EXTENSION_VERSION` marks
old copies `outdated` [repo]. Changes:

1. Register the minimal event set (§7.1). Keep `session_start` behavior,
   and keep the payload a superset of today's so the Rust side doesn't
   break.
2. Never `await` in a handler. Do the spawn and return. The spawn itself
   is a synchronous `posix_spawn` on Pi's event loop, around a
   millisecond (estimate, UNVERIFIED). That is why the extension must
   emit only on state transitions, never per streaming event.
3. Spawn with `detached: true` and `stdio: ["pipe","ignore","ignore"]`,
   then `unref()`. The writer gets its own process group, so a pane
   SIGHUP on exit doesn't kill it mid-write (INFERRED).
4. On `session_shutdown`, the parent may `process.exit` right after its
   handlers run [S14]. Pass the payload so it survives the parent's exit:
   in argv or an env var (small, metadata-only), or as a synchronous
   stdin write. An async pipe write might not flush (INFERRED).
5. Include `pid: process.pid`, a per-instance `seq`, `instance` (random
   per factory load, since `/reload` resets module state), and
   `observed_ms: Date.now()`.

Transport options:

| Option | How | Pros | Cons |
|---|---|---|---|
| **A. Spawn per transition (recommended v1)** | Today's mechanism, with coalescing | No new subcommand. Stays inside the ADR 0028 boundary (`hook write` is the interface). | A process plus a tmux call per transition. Exit detection relies on pid liveness. |
| B. One long-lived writer per session | Spawn `conspectus hook stream pi` once at `session_start`, write NDJSON lines to its stdin. The child forwards to the daemon or spool. | One spawn per session. **EOF on stdin = Pi died**, even on SIGKILL, because the kernel closes the pipe. Exact EXITED with no pid polling. | New subcommand (capabilities entry, ADR). The child must outlive pane SIGHUP. The extension must respawn it if it dies. |
| C. Extension writes a state file | `fs.writeFileSync` under `$XDG_STATE_HOME/conspectus/` | Cheapest | Bypasses the `hook write` boundary (ADR 0028). Duplicates root resolution. Rejected. |
| D. Extension connects to the daemon socket | `node:net` client | Lowest latency | Needs a daemon. Couples the protocol to Pi code. Still needs a spool fallback. Deferred. |

### 5.3 Latency (estimates, UNVERIFIED)

- **Event to `hook write` start:** under 5 ms (one spawn).
- **`hook write` total:** about 10–60 ms. Rust startup, an up-to-8-hop
  `/proc` walk, `tmux display-message`, daemon `hook_ingest`, and a spool
  rewrite under the writer lock (ADR 0146). Passing `pid` and
  `TMUX_PANE` in the payload would skip the walk and tmux lookup in the
  common case.
- **Ingest to TUI:** set by how the daemon pushes `hook_ingest` changes
  to clients. A refresh cycle replays the spool about every 5 s (ADR
  0146 context). The graph and TUI researchers should check whether
  ingest triggers an immediate client update.
- **Extension side:** Pi persists the entry *after* the extension
  handlers run [S11]. The hook therefore usually reports a transition
  before the file shows it.

### 5.4 Reliability and staleness

| Failure | Effect | Mitigation |
|---|---|---|
| SIGKILL, OOM, crash, fatal runtime error, dead-terminal EIO exit | No `session_shutdown`. The last state (often WORKING) is stuck. | Pid liveness check (exists in `hook_sidecar.rs`; needs a reliable pid, so send `process.pid`). Heartbeat TTL as a second backstop. Option B's EOF. |
| Writer spawn fails (binary missing) | No records | Already a silent no-op. `hook status` can't detect it. |
| Two writers race (no daemon) | Spool read-modify-write lost update (ADR 0146) | Per-pane key plus `seq` / `observed_ms` ordering. A heartbeat repairs a lost update. |
| Out-of-order arrival (with daemon) | Two `hook write` processes started ms apart reach `hook_ingest` in either order | The writer replaces a record only when `(instance, seq)` is newer, or `observed_ms` for a new instance. Today's `observed_epoch >=` in seconds lets the later *arrival* win. |
| Lost `tool_execution_end` | Stuck "tools" count | Self-contained snapshots: the next transition resends the full set. `agent_settled` clears tool and prompt state. |
| A tool runs for 20 minutes with no events | Looks frozen | Heartbeat with an unchanged state (§7.3) keeps it fresh. |
| `/reload` | Module state lost mid-session. Reload is normally only possible when idle (INFERRED). | Rebuild from `ctx.isIdle()` in `session_start{reload}`. |
| Unsupported older Pi | Events never fire | Registering an unknown event name is harmless (INFERRED: `on` stores handlers by name). Degrades to READY/WORKING only. |

**Staleness rule (proposal):**

- **EXITED, certain:** the record's `pid` is dead, a
  `session_shutdown{quit}` arrived, or the pane no longer runs `pi`.
- **Fresh:** `now - observed_ms` ≤ 150 s (2.5 × a 60 s heartbeat), for
  any state.
- **Stale:** beyond that with the pid alive, show the state as
  "unknown (last: X)". Don't drop it. If no pid is known (pre-CSP-630
  records), fall back to ADR 0028's 15-minute TTL, which the reader
  should then enforce.

## 6. Hook-free fallback: what the tail and mtime show

### 6.1 Tail reader

The §3.4 table, applied to the last 32 KiB the adapter already reads, as
a separate Tier 1 struct. Pair it with process evidence: a `pi` process
in a pane attributed to this session. Without the hook, attribution
itself is a guess from the command line and cwd (ADR 0121), so tail state
attaches to the *session* row with low confidence and to a mux only
through that guess.

### 6.2 What mtime means

- Pi doesn't hold the file open and writes only on entry boundaries. The
  mtime equals the last entry's timestamp.
- Streaming a long reply or running a long tool writes **nothing** until
  it ends. A file quiet for 5 minutes can still be WORKING.
- **Cache warming:** `cacheWarming` defaults to `"idle"`, which keeps
  prompt caches warm "for up to 30 minutes between runs" [S12]. It
  records non-message `usage` entries with `kind: "cache_warm"` [S25].
  An idle session's mtime and newest timestamp keep moving.
  - This also affects today's `last_active_epoch` in `pi.rs`, which takes
    the newest timestamp of any entry. It should skip `usage` entries.
    Live check needed (CSP-630). Possible follow-up bug.

### 6.3 Accuracy limits

The tail can tell, with medium confidence:

- generating (last `user` or answered `toolResult`)
- tools pending (`toolUse`)
- finished (`stop` or `aborted`)
- failed (`error`)

It cannot show WAITING, COMPACTING in progress, a queued follow-up, a
retry versus a settled error (only a window heuristic), STARTING, or
EXITED (only the process scan can). A stale "generating" means "pi died
or is very slow". It needs the process check.

### 6.4 `/new` before the first exchange

The file doesn't exist until the first user message [S10], and the
sidecar reader won't synthesize a session whose `transcript_path` is
missing [repo]. A live state for a fresh `/new` session therefore has no
session node to attach to. It must attach to the pane or mux until the
file appears. This is a question for the graph step.

## 7. Recommendation

### 7.1 Minimal event set (extension)

The extension registers:

- `session_start`
- `session_shutdown`
- `agent_start`
- `message_end` (assistant only; read `stopReason` and classify
  `errorMessage`)
- `tool_execution_start` and `tool_execution_end` (top-level only)
- `ui_prompt_start` and `ui_prompt_end`
- `session_before_compact`, `session_compact`, `session_compact_failed`
- `agent_end` (marks the retry gap)
- `agent_settled`
- `after_provider_response` (optional; only acts on status ≥ 400)

It does **not** register `message_update`, `tool_execution_update`,
`provider_stream_event`, `tool_call`, `tool_result`, or `context*`.
Those are high-frequency or payload-bearing.

### 7.2 Extension state machine and emitted snapshot

The extension keeps this state:

- `run` (bool)
- `compacting` (bool, plus `reason`)
- `prompt` (null or kind)
- `tools: Map<toolCallId, isSubagent>`
- `lastOutcome`: `completed`, `error`, `aborted`, `length`, or `deferred`
- `errorClass`: `rate_limit`, `overloaded`, `auth`, `context_overflow`,
  `network`, `provider`, or `unknown`, classified **inside** the
  extension
- `retrying` (bool)

Derived `state`, in priority order (mirrors Pi's reporter):
WAITING > COMPACTING > (run active: RETRYING > SUBAGENTS > WORKING-tools
> WORKING-generating) > resting (ERROR | READY-interrupted | READY).

Snapshot payload sent to `conspectus hook write pi` (every field is an
enum, count, id, or path; no text):

```json
{
  "session_id": "<id>", "cwd": "<cwd>", "transcript_path": "<file>",
  "hook_event_name": "live:<pi event name>",
  "pid": 12345, "instance": "<random>", "seq": 42, "observed_ms": 1794400000000,
  "extension_version": "2", "pi_version": "<if exported>",
  "live": {
    "state": "working|waiting|ready|compacting|error|exited|detached",
    "detail": "generating|tools|subagents|retrying|rate_limited|interrupted|permission|question|custom|manual|threshold|overflow|run_failed|compaction_failed",
    "tools_in_flight": 2, "subagents_in_flight": 0,
    "error_class": "rate_limit", "since_ms": 1794399990000
  }
}
```

Emission policy:

- **Send at once:** WAITING enter and exit, READY, ERROR, EXITED,
  DETACHED, COMPACTING enter and exit.
- **Coalesce** changes between WORKING sub-states (generating and tools)
  with a trailing debounce of about 500 ms. Cancel the debounce when an
  immediate transition fires.
- **Heartbeat:** every 60 s, an unchanged snapshot. The timer starts in
  `session_start`, is `unref()`'d, and is cleared in `session_shutdown`.
  It never touches a captured `ctx`.

### 7.3 Event → state transitions

| Event (condition) | New state | Notes |
|---|---|---|
| `session_start` (any reason) | READY (detail none). WORKING if `!ctx.isIdle()`. | Reset counts. New `instance`/`seq` after `reload`. Carries attribution as today. |
| `agent_start` | WORKING/generating | Clears `retrying`. Sets `run`. |
| `tool_execution_start` (no `parentToolCallId`) | WORKING/tools, or WORKING/subagents if `toolName` is in the subagent set | Debounced |
| `tool_execution_end` (no `parentToolCallId`) | WORKING/generating when the set is empty | Debounced |
| `message_end` (assistant, `stopReason=error`) | unchanged; sets `lastOutcome=error`, `errorClass` | Text never leaves the extension |
| `message_end` (assistant, other) | unchanged; sets `lastOutcome`, clears `errorClass` | Matches the reporter: the latest response wins |
| `after_provider_response` (`status==429`) | detail `rate_limited` while run active | Optional |
| `agent_end` (lastOutcome=error) | WORKING/retrying | The gap until the next `agent_start` or `agent_settled` |
| `ui_prompt_start{kind}` | WAITING/permission (confirm), WAITING/question (select, input, editor), or WAITING/custom (custom; low confidence) | Immediate |
| `ui_prompt_end` | Recompute | Immediate |
| `session_before_compact{reason}` | COMPACTING/reason | Immediate |
| `session_compact` | Recompute. WORKING if `willRetry`. | |
| `session_compact_failed{aborted, willRetry}` | Recompute. ERROR/compaction_failed when not aborted and not `willRetry`. | |
| `agent_settled{aborted}` | READY/interrupted if aborted. ERROR/run_failed if lastOutcome=error. Otherwise READY. | Clears `run`, `tools`, `retrying`. Leaves `prompt` alone (prompts can outlive runs). |
| `session_shutdown{quit}` | EXITED | Send so it survives the parent's exit (§5.2 item 4) |
| `session_shutdown{new\|resume\|fork\|reload}` | DETACHED | `session_start` follows with the new identity |
| heartbeat | unchanged | Refreshes `observed_ms` |

### 7.4 Rust-side implications (for the graph step)

These are notes only; each needs its own ADR.

- The spool key must include `pane_id`, falling back to `pid`, then cwd.
  Without that, live state is wrong for multi-pane tmux sessions. This
  affects attribution too.
- `HookRecord` gains an optional `live` object and `observed_ms`, plus
  `instance` and `seq` for ordering. Either `schema_version` 2 or
  additive optional fields. Readers ignore unknown fields today (serde
  defaults), but `write_record` rejects `schema_version != 1`.
- Pi's `hook_record_from_payload` should accept a payload `pid` and trust
  it over the comm walk. This resolves CSP-630 #4 by design.
- Enforce a TTL in the reader. `ACTIVE_TTL_SECONDS` is unused today.
- A Pi `is_subagent_process` that recognizes a `pi` whose parent chain
  includes a `pi`. Because `process.title` overwrites the child's argv,
  `--mode json -p --no-session` is not visible in its cmdline (INFERRED).

### 7.5 Fixture plan

1. **Hook payload fixtures:** `tests/fixtures/pi/live/payload-*.json`.
   One per state and detail, plus legacy payloads without `live` and with
   an unknown `state`. They exercise `hook_record_from_payload` and the
   reader's state and staleness logic: pid dead, past TTL, out-of-order
   `seq`, a new `instance`.
2. **Event-script fixtures:** `tests/fixtures/pi/live/script-*.jsonl`.
   Each line is one extension event, metadata fields only, followed by
   the expected snapshot. Scripts:
   - `tool-run`
   - `parallel-tools`
   - `permission-gate-during-tool`
   - `plan-mode-prompt-in-agent-end`
   - `retry-then-success`
   - `retry-exhausted`
   - `rate-limit-429`
   - `threshold-compaction`
   - `overflow-compaction-retry`
   - `compaction-failed`
   - `abort`
   - `new-session-switch`
   - `reload`
   - `subagent-parallel`
   - `shutdown-quit`
   - `kill-no-shutdown`

   They define the reducer contract. The repo has no Node, so either the
   reducer gets a Rust mirror used only in tests, or adding Node to the
   dev shell gets its own ADR. Either way, CSP-630-style live checks
   confirm the TypeScript side.
3. **Tail fixtures:** `tests/fixtures/pi/live/tail-*.jsonl`. Synthetic
   session files ending in each §3.4 row. Include an `assistant stop`

4. **Live checks** (extend CSP-630):
   - Record the real event order for a tool run, an Esc abort, a forced
     retry, `/compact`, and a `permission-gate` prompt.
   - Confirm that `context_edit` follows a retried error.
   - Confirm `session_shutdown` arrives on tmux `kill-pane` (SIGHUP

   - Measure the `hook write` round-trip.

## 8. Open questions for the operator

1. **Version floor.** Is 1.1.0 an acceptable minimum for full fidelity,
   with WAITING needing at least 0.84.4? Which Pi version runs on the
   operator machine?
2. **`kind: custom` prompts.** Show them as WAITING (possible false
   positives from loaders and widgets), as a separate low-confidence
   "extension UI" state, or not at all?
3. **Subagent tool names.** Is the default set `{"subagent"}` enough, or
   do you run a third-party subagent package with other tool names?
   Should the set be configurable in Conspectus config and passed to the
   extension (through an env var or a regenerated extension file)?
4. **Error detail.** Classifying `errorMessage` into an enum inside the
   extension never persists the text. Is that within ADR 0086 as you read
   it, or should ERROR stay classless (only "run failed" and "rate limited
   by HTTP 429")?
5. **Transport.** Start with spawn-per-transition (A) and move to a
   long-lived `hook stream` writer (B) only if needed, or go straight to
   B for exact EXITED detection?
6. **Heartbeat cost.** Is one `conspectus` spawn per minute per running
   Pi acceptable?
7. **Fresh `/new` sessions.** Before the first exchange, should live
   state show on the pane/mux row, given that no session row exists
   until the file does?
8. **Detected but not surfaced.** Should provider login (`auth`) and
   built-in selectors stay invisible? They can't be detected without
   scraping.
9. **Node in the dev shell.** Add Node so the TypeScript reducer can be
   unit tested (needs an ADR), or keep the extension reducer verified only
   through fixtures and live checks?
